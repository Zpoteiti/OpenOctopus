# Pydantic AI Harness 运行时替换

状态：已实现；开发环境回归、真实服务集成和本地模型验收完成。
日期：2026-10-03。
代码基线：`d5e97c0a7a05`。

## 1. 目标与已确认的边界

最大化采用社区维护的 Pydantic AI、Pydantic AI Harness 及其官方持久化执行集成，删除被替代的自研实现。OO 负责产品权限、设备连接和业务规则；模型协议、Agent 循环、上下文管理、通用记忆及执行恢复优先使用上游实现。

用户已确认：

- 长期记忆允许改用官方存储；前端必须继续支持用户查看、编辑。
- 主代理和子代理必须在服务重启后自动恢复执行，无需用户再发一条消息。
- 可以一次性修改内部接口、数据库结构及前端，不建设历史数据迁移或旧运行时兼容层。
- 多用户隔离是必需能力。设备路由与服务器、客户端工具继续纳入同一 Agent 执行路径。

实施采用一个完整任务、分阶段验收。保留产品行为不等于保留原实现；某个旧模块只有在官方确实不覆盖其职责时，才保留其中必要部分。

本设计接替[上下文压缩与历史恢复草案](2026-10-03-context-compaction-and-history-recovery.md)的实施方向，继承原始记录可恢复、工具配对、用户隔离等要求；不实施该草案自定义的压缩选取算法、固定摘要结构及双阶段状态机。

## 2. 技术选择与验证状态

采用 **Pydantic AI + Harness + DBOS + PostgreSQL**。

2026-10-03 查验的发行基线为 Harness `0.54.0`、Pydantic AI Slim `2.54.0`、DBOS `3.2.0`。已安装上述发行包并验证主/子代理、动态工具、Memory、Skills、流式事件和 DBOS 的组合。TypeSafe SDK 固定为 `0.7.2`。升级必须重跑进程恢复测试。

- Pydantic AI：模型适配、消息类型、工具注册、执行循环和事件。
- Harness：Memory、压缩、结果外存、历史检索、Skills、子代理等按需组合。
- DBOS：执行日志、步骤恢复、持久化排队、消息与定时调度。
- PostgreSQL：复用现有数据库服务；OO 产品表、官方 Memory 表和 DBOS 管理的执行表职责分开，使用同一数据库以支持事务入队。
- RustFS：继续存附件和 workspace 文件。工具结果外存通过官方 OverflowStore 接口存入 PostgreSQL，随会话删除；单个结果上限 16 MiB。Memory 使用官方 PostgreSQL 表。

DBOS 是当前实施目标：可嵌入现有 Python 服务，并复用 PostgreSQL。先保留单个 ASGI 服务进程，不因此引入 Redis 或单独的工作流服务。

**接入 DBOSDurability 并不自动使所有工具持久化。** 官方文档明确区分模型/MCP/动态工具集和普通函数工具；后者的 I/O 需要显式持久化边界。Memory 工具同样需要适配。Agent、能力与需要持久化包装的工具集在启动时注册，按用户变化的数据通过运行依赖和预注册动态工具集解析。

**StepPersistence 不承担自动执行恢复。** 它提供快照和执行记录，不能单独满足本项目的恢复要求；不再围绕它自研一套恢复引擎。

M1 必须先证明主子代理、官方 Memory、动态工具和流式输出能共同恢复。若只能通过维护 SDK 私有分叉实现，应报告具体缺口并重新评估该集成，不能默默新增另一套 Agent 循环。

## 4. 运行身份、输入和存储

每次运行携带可序列化的用户 ID、会话 ID、运行 ID、父运行 ID、权限配置和模型配置版本。池、数据库 Session、WebSocket、锁和 SDK 客户端由进程管理，不进入工作流参数。密钥引用在实际执行边界解析；避免把密钥放入执行日志或前端事件。

会话中的每次 SDK 调用有独立 run ID；重启恢复保持同一执行身份。用户新发起的重试、显式继续则创建新运行，并记录关联关系。子代理有独立会话历史，保留直接父级和根任务归属。

接入流程：

1. 验证真实用户/渠道身份，确定权限与目标会话。
2. 在同一数据库事务保存输入，并通过 DBOS 的事务入队接口提交工作；事务失败则二者均不存在。
3. 主会话队列使用会话分区、每分区一个活动执行者。工作流在持久化边界捕获输入批次，新到消息不归入已经捕获的批次。
4. 用官方 Agent 执行捕获的工作；产品历史及状态投影通过幂等事务提交。
5. 浏览器订阅运行事件；断开浏览器连接不终止后台执行。

先验证 DBOS 事务入队与现有 SQLAlchemy async 连接的组合，使用官方 `run_sync` 桥接方式；不为这一环另造 outbox 消费框架。

官方 `ModelMessage` 序列化作为模型历史表示，存于 PostgreSQL。OO 的发送者、附件、渠道投递及所有权元数据单独保存。DBOS 日志负责恢复执行；产品消息表负责历史查询和前端显示，两者不能独立驱动同一个任务。

模型有效上下文与不可变的原始对话证据分开：压缩改变下次请求，不删除用户可查询的原始内容。大附件和工具结果采用持久引用，避免每一步重复存入工作流参数。

删除会话时，先阻止该会话新入队并取消相应运行树，再清理会话、委派记录和不再被引用的对象；用户共享的长期记忆保留。删除账户时，停止全部所属工作并额外清理该用户的官方 Memory。已取消或已删除的工作不能被启动恢复重新激活。

## 5. 自动恢复合同

最低要求是：同一已部署版本的服务器进程退出或被强制终止，PostgreSQL 与持久对象仍可访问时，服务启动后自动继续已接受的主、子代理工作。不依赖浏览器在线、再次发送消息或管理员手动调用 resume。

恢复以完成步骤为边界，不承诺恢复 Python 堆栈或已经发出的每个 token。已完成步骤使用保存结果；未完成模型请求可以重新请求并产生新响应。恢复中的临时文本由前端替换为新尝试，不能拼接成重复答案或重复计入已完成输出。

| 中断位置 | 必需行为 |
| --- | --- |
| 输入事务提交前 | 没有已接受任务；客户端重试使用接入幂等标识 |
| 输入已提交、尚未开始 | 持久队列自动启动同一任务 |
| 模型请求进行中 | 重新执行未完成请求；替换对应预览尝试，保存的历史不重复 |
| 模型结果已完成 | 重放保存结果，继续未完成的工具或后续步骤 |
| 工具尚未下发 | 重查当前权限后执行 |
| 工具结果已经持久化 | 返回保存结果，不再调用外部工具 |
| 工具可能执行、结果未持久化 | 查询执行回执或状态；可证明幂等才重试；否则形成明确的结果未知信息供恢复流程处理 |
| 子代理结束、报告尚未被父级消费 | 持久投递到直接父级；重复恢复不造成重复模型输入 |
| 父级已结束、后台子代理仍在运行 | 子代理独立恢复；完成后自动排入父会话继续运行 |
| 用户明确取消 | 持久取消主任务及应取消的后代；重启不能撤销用户的停止操作 |

### 外部副作用

数据库工作流不能使任意外部 Shell、MCP 或渠道 API 与本地事务原子提交。工具调用必须有稳定的逻辑操作标识与经过检查的恢复策略：

- 读取：允许重新读取，但保存结果后重放该结果。
- OO 数据库变更：使用官方事务步骤或等价的幂等事务提交。
- 官方 Memory：使用其版本比较与操作回执，再补齐 DBOS 工具步骤边界。
- 设备/对象存储变更：有版本、任务 ID、结果回执时先核实并接续。
- 任意外部命令或不支持去重的 API：不能把连接失效等同于未执行；结果未知时先检查外部状态，不自动重复副作用。

适配层只处理操作身份、去重与核实，不实现新的 Agent 循环。需要时扩展客户端结果回执/状态查询合同；设备路由、取消和 generation 隔离继续适用。第三方服务无法证明的执行结果必须如实呈现。主/子代理仍自动恢复，不以把整个运行标记为 abandoned 代替恢复。

服务重启与版本升级分开处理：固定版本的恢复是本次硬要求。升级 SDK 时先停止接收新任务并排空活动工作，再切换版本；不能修改活动工作流的步骤定义后假定旧执行日志仍可重放。不建设跨版本数据迁移层。

## 6. 子代理与多用户

主会话串行不等于用户的所有工作串行。不同会话以及可并行的子代理可以同时运行，但共享根任务预算和用户资源上限。

子代理应采用官方独立历史、工具定义、深度限制及委派语义。执行适配必须将后台子代理接到持久工作流；不得把内存 `asyncio.Task` 作为唯一执行者。子代理等待不占用父会话同一串行队列槽，否则会死锁。

官方 `DelegationTasks` 的文件记录与自动恢复执行不是同一能力；其恢复记录不会自动执行工具。实测 managed delegation 的动态报告能力无法直接与 DBOS 组合，因此使用公开 `WrapperAgent` 包装官方前台 `SubAgents`，后台 `delegate_background` 启动同一种 DBOS 子工作流。结果进入 OO 的事务接入队列并唤醒父级；没有修改上游私有循环。

首版允许一层子代理；每个根运行最多 8 个子代理，单个子代理最多 50 次模型请求，全树共享 200 次请求预算。预算和父子关系写入 PostgreSQL，重启后不重置。子会话在会话列表可查看，继续任务通过父会话进行。

后台完成事件必须形成持久报告或消息。报告投递、确认和父会话唤醒采用稳定 ID；父级忙碌时进入其后续边界，空闲时自动启动继续运行。报告属于工具/自动化结果，不能赋予新的用户权限。

权限来自服务端身份及当前授权。子代理权限不得超过父级；`message_only` 不得通过委派获得设备、workspace 或私人记忆访问。取消或撤销权限后，恢复中的任务在下一次真实外部操作前重新检查，不复用历史授权结果放行。

运行依赖可共享不可变的归属信息，不能共享可变的“当前用户”、当前历史、数据库 Session 或 MCP 凭据状态。并行子代理的状态和预算必须经过进程重启验收，不能只验证单用户示例。

## 7. Memory 与前端

采用官方 `PostgresMemoryStore`，服务管理其连接池。主记忆与主题笔记都属于用户命名空间；命名空间由经过认证的服务端用户 ID 派生，不作为模型可填写的参数。

第一版主代理与有权限的子代理共用同一用户笔记本，不自动为每个临时子代理建立另一套永久记忆。只读或受限代理暴露相应工具子集。代理临时过程记录仍属于该子代理会话。

前端提供笔记列表、查看、编辑与允许的删除操作，直接通过官方 Store 公共接口读写同一份数据。编辑保存带版本前提；冲突返回用户可见的重新加载选择，不能覆盖代理或 Dream 的并发更新。分页读取与完整编辑需遵守大小上限，不能把截断前缀当完整文件保存。

SDK 中的 `MEMORY.md` 是主笔记名，不再要求它物理存在于旧用户 workspace。移除旧 workspace 特殊记忆入口及系统提示词注入，提供 Memory 入口；不做两处同步，也不保留假装可编辑的旧文件副本。`SOUL.md` 和普通 workspace 文件照常存在。

自动注入、记忆工具与记忆组织采用官方机制。持久执行下，快照和工具变更都要落在正确步骤边界；特别验证“写入成功但步骤结果未提交”后不会追加两次。

Dream 改为读取、更新同一官方 Store。保留来源证据、受控整理、版本冲突处理和撤销；撤销只在目标版本仍匹配时应用。Dream 与前端不能直接绕过官方 Store 的版本/幂等合同更新其底层表。

## 8. 上下文、工具和模型

使用官方压缩能力、工具结果外存和历史检索。与 Memory 组合顺序遵循上游约定。具体阈值优先配置官方参数，不重做压缩器。历史检索通过公开来源接口接入 OO 已保存消息，限定在当前授权会话；不为检索额外引入 MongoDB。

保留：当前用户需求、完整工具调用/结果配对、原始证据、有限存储和检索范围。压缩失败不提交损坏历史；超长结果应在展示截断前进入受限的持久存储。上游采集限额已经丢弃的内容不能声称可恢复。

Provider 首批覆盖 Anthropic Messages、OpenAI Chat Completions 兼容接口及 OpenRouter 的对应官方实现。LiteLLM/vLLM 按实际暴露协议接入，不强制所有平台先转换成 Anthropic。协议、模型与 endpoint 分开配置；公开 URL 到实际请求路径须测试。

模型配置在逻辑运行中按版本引用，恢复时仍指向正确 endpoint/model；不允许仅凭模型名称被重新解析到另一个供应商。`ResolveModelId` 等解析器遵守官方确定性/I/O 限制；凭据和客户端不作为可序列化 deps。

图片回退只对明确的兼容错误执行，保留原始图片和工具结果；已有可见输出后不在同一次预览上透明重试。重启恢复属于新尝试，前端明确分段。SDK、HTTP 客户端、DBOS 三层重试预算统一，防止重试次数相乘。

第一版保持同轮工具顺序执行，显式设置官方串行模式。多会话/子代理并发单独控制。所有 OO 工具接入官方参数校验、结果与错误通道；从 JSON Schema 包装时验证是否真正执行校验，不仅生成描述。

## 9. 流式事件、停止和恢复界面

DBOS 下直接使用流式迭代 API 可能只在步骤完成后重放模型事件。采用官方 durability 事件处理入口获取实时事件，模型/工具事件统一关联用户、会话、运行、尝试和子代理。

临时 token 预览可以丢失，已提交消息和终态不能丢失。恢复后的新尝试替换旧预览；稳定事件与结果保存幂等，前端重连从产品历史重建。不得双重注册实时与重放处理器而重复发布同一事件。

Stop 通过工作流取消 API 持久记录，并向运行中的 OO 远端工具发送可行的取消请求。工作流被取消不代表外部命令已停止；保留取消后的结果核实和迟到消息处理。父子取消、用户删除及正常服务退出分别测试。

## 10. Cron、Heartbeat、Dream 与自主唤醒

采用 DBOS schedule 和延迟队列，替换通用 ticker、睡眠和重启扫描。OO 的 schedule ID 包含用户/任务归属，管理 API 始终按已认证用户限制范围。

- Cron 使用现有 croniter 解释表达式与 IANA 时区；`cron`、`every`、`at` 的下次时间通过 DBOS 延迟队列执行。任务配置、下次时间与持久入队在同一 PostgreSQL 事务提交。保留时间计算以避免配置表与独立动态 schedule 形成两处调度状态。
- 保留已有的“错过的周期不集中补跑”和“忙碌时跳过新触发”规则。不要打开无界 backfill；已接受的运行与尚未触发的错过时刻是两回事。
- 已接受的 Cron/Heartbeat 运行中断后自动恢复；尚未接受且过期的一次性任务仍按原规则跳过。
- Heartbeat 使用 DBOS 半小时 schedule，Dream 使用每分钟资格检查 schedule，关闭 backfill。超过计划时刻 5 秒的新脉冲跳过；每用户通过官方队列去重，忙碌时不积压。Heartbeat 保留文档解析、Jev 决策与 Phase 2 正常 Agent 执行。
- Dream 保留当地日期、未处理来源和证据整理规则；其阶段改为持久工作流，删除手写 ticker；准备记录继续承担来源证据、Memory 写入回执和撤销版本检查。
- 子代理完成、外部结果到达和定时触发都通过同一授权接入边界唤醒代理。

配置变更、暂停或删除与触发并发时，在真正接受工作前重查任务版本。公开配置与调度提交若不能在单事务修改，使用 DBOS 工作流完成该配置操作及幂等修复，避免两个相互独立的调度真相。

## 11. 实施顺序与退出标准

| 阶段 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| M1：持久化可行性 | 固定依赖、最小 DBOS 主/子运行、官方 Memory、动态工具、实时事件 | 真实子进程强杀后自动恢复；至少一个后台子代理恢复并唤醒父级；Memory 不重复写；事务入队正确 |
| M2：Provider 与主循环 | 官方模型、消息、Toolset、主循环、PostgreSQL 历史与前端事件 | 文本、reasoning、图片回退、服务器/客户端/MCP 工具、多用户与同会话排队、取消通过；恢复不走 abandon |
| M3：Memory 与上下文 | 官方 Store 与前端编辑、压缩、外存、回读、Skills | 编辑冲突正确；压缩后原文可查；大结果重启可读；受限用户不能读取其他作用域 |
| M4：完整子代理 | 前台/后台委派、父子事件、预算、权限、自动唤醒 | 多用户并发树、子代理中断、父级空闲/忙碌、重复报告、停止后重启均正确 |
| M5：自动化与收尾 | 调度替换、Dream/Jev 接入、全入口验收、删除旧代码及更新合同文档 | Cron/Heartbeat/Dream、Web/Discord/钉钉均调用新执行路径；客户端必要改动跨平台验证 |

M1 是可行性关卡，不是最终交付。其结论记录准确失败窗口与实测版本。不能用异常捕获、同进程重建对象或只重启 HTTP 客户端来代替真实进程恢复测试。

## 12. 必需测试矩阵

1. **崩溃恢复**：输入提交、模型步骤、工具下发前后、工具结果落库前后、子任务完成与父级确认前后分别强杀；重启后无需新输入继续。
2. **副作用**：完成结果不重发；同一记忆操作只生效一次；不可确认的非幂等外部操作不会盲目重试。
3. **隔离**：两用户各多会话；伪造会话/子任务/记忆/结果 ID 被拒绝；配置、凭据、设备目标与事件不串用户。
4. **输入归属**：捕获输入后又到消息、延迟注册预览、工具执行期间新输入、浏览器断开和重连。
5. **取消**：模型中、工具已下发、后台子代理、父等待子、账户删除；取消后重启不恢复已停止任务。
6. **前端**：记忆查看编辑、版本冲突、恢复状态、重复事件去重、会话切换后的迟到事件。
7. **自动化**：时区/DST、错过边界、忙碌跳过、暂停/删除竞争、已接受任务重启、Dream 整理和撤销冲突。
8. **模型兼容**：精确请求路径、工具参数、reasoning 往返及公开投影、图片降级、不同 endpoint 同名模型、重试预算。
9. **真实集成**：现有 PostgreSQL/RustFS/客户端路径、至少一个实际可用模型端点。Mock 验证协议，不声称验证了企业所有部署；未提供端点的平台列明未实测。

沿用项目 lint、类型检查、Server/Frontend 测试与必要的真实设备/冻结客户端检查。真实企业模型端点仍需要提供凭据后进行部署验收；协议测试使用真实 SDK 与本地响应夹具，不等同于企业平台验收。

## 13. 收尾与维护

删除替代后的旧 Agent 循环、Provider 协议代码、压缩器、Memory 文件注入、ticker 和旧恢复状态路径；不长期保留两套执行后端。工具实现中仍承担设备业务的部分保留，并缩减到 SDK 工具适配所需边界。

同步更新 `DEVELOPMENT.md`、API、工具/设备协议、数据库说明与相关测试。新增 OO 适配必须说明上游缺口、产品理由及对应验收，避免逐步复制上游运行时。

“社区频繁更新”采用固定版本、小步升级、运行合同回归的方式利用；不让运行中的持久任务自动切换 SDK 版本。升级验证尤其覆盖工具序列、Memory 幂等、子代理恢复与事件投影。
